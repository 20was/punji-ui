# Contributing to Punji UI

Thank you for helping. This page covers the setup, the checks, the bar a new
component has to meet, and how releases work.

## Setup

You need Node 24 (see `.nvmrc`) and npm 11.

```sh
git clone https://github.com/20was/punji-ui.git
cd punji-ui
npm ci --ignore-scripts
```

## The checks

`npm run verify` runs every gate CI runs, in order:

| Script | What it checks |
| --- | --- |
| `npm run lint` | oxlint (correctness, React hooks, jsx-a11y, imports) and the CSS token guard |
| `npm run typecheck` | TypeScript, strict |
| `npm run test` | Vitest in jsdom, including axe-core on every component |
| `npm run build` | `tsc` to ES modules and types, Lightning CSS for the stylesheets |
| `npm run size` | size-limit budgets for every component and the CSS |
| `npm run check:package` | publint, are-the-types-wrong and the tarball allowlist |

Before pushing, run `npm run verify:deep`: `verify` plus every test again with
2000 inputs per property test (`npm run test:deep`), so a rare input fails on
your machine rather than in CI. A property failure prints its seed and path;
pass them to that `fc.assert` (`{ seed, path }`) to replay it, fix the cause,
then remove the pin. Tests never depend on `Math.random` or the clock: fake
timers and fast-check's seeded inputs only. CI runs the same steps once; please do not
push to "see if CI passes".

## Where the code lives

The kit is developed inside Punji's app, the one source of truth, and mirrored
here automatically. Issues, ideas and discussion are welcome in this
repository; code changes are made upstream by the maintainers. Nobody edits
the generated code here by hand: everything under `src/` except
`src/internal/`, the stylesheets, `docs/tokens.md`, `.size-limit.json` and the
`exports` map in `package.json`. The "Generated files come from the sync" CI
check fails a pull request that changes them, unless it comes from the sync
branch or a maintainer adds the `manual-change` label (for a change to the sync
itself). Later, once the kit is stable, this repository may become the source.

## How the kit is kept in sync with Punji

The [Sync workflow](./.github/workflows/sync.yml) runs every 6 hours (and on
demand: Actions, Sync, Run workflow). It checks out Punji's main branch, runs
the sync, and stops if nothing changed. Otherwise it runs
`npm run verify:deep`, opens or updates the `sync/punji-web` pull request
("chore(sync): mirror the kit from Punji @<commit>") with a patch changeset,
and turns on auto-merge, so it merges itself once CI passes. If the sync meets
something it cannot classify, the job fails and opens no pull request: that is
the signal for a maintainer to update `scripts/sync/manifest.mjs`.

It needs one secret, `PUNJI_SYNC_TOKEN`: a fine-grained token that reads
Punji's repository and writes contents and pull requests here (a pull request
opened with the workflow's own token would not run CI).

Maintainers can run the same sync by hand:

To mirror the current kit:

```sh
PUNJI_WEB_DIR=/path/to/a/punji/web/checkout npm run sync
# or: node scripts/sync-from-web.mjs --from /path/to/a/punji/web/checkout
npm run verify
```

Then open a pull request with the diff and a changeset. The script:

- copies every kit module that `scripts/sync/manifest.mjs` marks **ship** or
  **adapt**, rewrites its imports, and applies the documented adapter edits
  (for example, `href` renders `<a>` or the `linkComponent` you pass, so the
  package needs no router);
- splits the kit's stylesheet into `src/styles/<module>.css` inside the
  `punji.components` layer, and maps the theme's tokens to `--pu-*` in
  `src/styles/tokens.css` and [docs/tokens.md](./docs/tokens.md);
- regenerates `src/index.ts`, the `exports` map in `package.json`,
  `.size-limit.json` (budgets from the manifest) and the README's component
  table;
- removes files it generated before and no longer produces.

An adapter edit that names its `upstream` change is skipped, with a note,
once Punji has the same fix: the next sync drops it from the manifest.

It **fails and writes nothing** when it meets something it does not know: a
new kit module, a class or keyframes no module owns, an adapter edit whose
target text changed, an import other than React, a helper in
`src/internal/` whose source changed, or a line that names something internal
(the public-repo denylist). Each of those is a decision: classify the module
(ship, adapt, pending with a reason, or web-only with a reason), adjust the
adapter, or review the hand-written helper. The sync is idempotent: running it
twice on the same source changes nothing the second time.

Files under `src/` that start with "Generated by scripts/sync-from-web.mjs",
`src/styles/*.css`, `docs/tokens.md`, `.size-limit.json` and the `exports`
field are generated. `src/internal/` (the link adapter and the number
helpers) and the tests are written here by hand.

## The bar for a new component

A component joins the kit only when all of this is true. The pull request
template repeats it as a checklist.

1. **It is general purpose.** Useful in any product: a dashboard, a store, a
   form, an admin tool. Product-specific pieces stay in the product.
2. **It follows a WAI-ARIA pattern.** Name the [APG pattern](https://www.w3.org/WAI/ARIA/apg/patterns/)
   it implements (or the native element it wraps) and implement its keyboard
   model in full. Prefer the platform: `<button>`, `<a>`, `<input>`, `<dialog>`,
   the Popover API.
3. **It has no runtime dependency.** `dependencies` stays empty. If something
   seems to need a library, open an issue first.
4. **It has a budget.** Set its `budget` in `scripts/sync/manifest.mjs` (the
   sync writes `.size-limit.json`): the measured size plus a little headroom.
   A typical control is under 1 kB gzipped; anything larger explains why.
5. **It uses tokens only.** Colours, sizes, radii and motion come from `--pu-*`
   variables; the token guard fails on a raw colour. It works in light and dark,
   draws one focus ring, has 44 px touch targets on touch screens and respects
   `prefers-reduced-motion`.
6. **It is tested.** Behaviour (pointer and keyboard), the ARIA roles and names,
   and an axe-core run with no serious or critical violation.
7. **It is documented.** A page on the documentation site: examples, props, when
   to use it, do and don't, content guidance (English and Nepali) and
   accessibility notes.
8. **It is exported twice.** From the root (`@punji/ui`) and from its own subpath
   (`@punji/ui/<name>`), with its own CSS file under `@punji/ui/css/`.

## Changesets and releases

Every pull request that changes what ships adds a changeset:

```sh
npm run changeset
```

Before 1.0, a breaking change is a **minor** and everything else a **patch**.
Write the summary for the people who use the package.

On merge to `main`, the release workflow opens or updates a "Version packages"
pull request. Merging that pull request publishes to npm from GitHub Actions with
Trusted Publishing and provenance, tags the release and creates a GitHub release
with the changelog and an SBOM. Nobody publishes from a laptop.

## Commits and pull requests

- One change per pull request, from a branch. `main` is protected.
- Conventional commit titles: `feat(button): …`, `fix(segmented-control): …`,
  `docs: …`, `ci: …`, `chore: …`.
- Keep the diff to what the change needs.

## Security

Never report a vulnerability in an issue or pull request. See [SECURITY.md](./SECURITY.md).

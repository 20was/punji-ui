# Integrating Punji UI into Punji Web

Date: 2026-10-31. A plan, not an implementation. Nothing in `punji-web` was changed, installed or
built to write it. Items I could not check are marked **unverified**. The inventory behind it is
[COMPONENT-INVENTORY.md](../COMPONENT-INVENTORY.md).

Goal: `@punji/ui` (this repository) is the single source of truth for reusable UI. `punji-web` consumes
a published, exactly pinned version of it and keeps only product-specific code.

## 1. How punji-web gets the kit today (facts)

| Fact | Where |
|---|---|
| `@punji/ui` is **not** a dependency. The name is an alias to local source: `@punji/ui` resolves to `src/components/kit/index.ts`, `@punji/ui/<kebab-name>` to `src/components/kit/<Name>.tsx`, `@punji/ui/styles.css` to `src/styles/kit.css` | `scripts/punji-ui-alias.mjs` (Vite and Vitest), `tsconfig.app.json` `paths` (169 entries) |
| The alias list is generated from the directory; a test fails when `tsconfig.app.json` drifts | `scripts/__tests__/punji-ui-alias.test.mjs` |
| The comment in the alias file says the kit "moves into its own workspace package after the public site is on it, then it is published" | `scripts/punji-ui-alias.mjs` |
| 136 non-test app files import `@punji/ui`; 40 docs-site files; 32 files import the kit by relative path | `src/**` |
| Kit CSS is 33 files (`kit.css` plus 32 `kit-*.css`, about 4,560 lines), none using `@layer`; `kit.css` imports the others; reads `--color-*`, `--space-*`, `--radius-*`, `--font-*`, `--text-*` | `src/styles/kit*.css` |
| Tokens are vendored from the app monorepo (ADR-6) into `tokens.source.json` and `tokens.generated.css` (`--v2-*`), and the account theme is `me-theme.css` | `scripts/sync-tokens.mjs`, `src/styles/` |
| Props tables of the docs site are generated by reading kit TypeScript; module sizes are measured by bundling each kit file from source | `scripts/design-props.mjs`, `scripts/kit-size.mjs`, `scripts/kit-size-budgets.json` |

| Rules: all UI through the kit (`AGENTS.md` rule 6); account pages may import only specific component folders | `src/me/__tests__/kitOnly.test.ts`, `pageCss.test.ts`, `flatSurfaces.test.ts` |

What punji-ui provides today: reverse sync retired (`scripts/sync-from-web.mjs` throws); `src/` is owned
here; ESM plus declarations, per-module CSS and an aggregate `styles.css`, `use client` retained;
Changesets with Trusted Publishing and provenance, gated by `UI_NPM_RELEASE_ENABLED` and the protected
`npm` environment; version `0.0.0`; `engines.node >=22.12`; React 19 peers. `scripts/portal.mjs` bridges
into a punji-web checkout to run the docs read-only. `scripts/sync/manifest.mjs` is kept as historical
classification (97 modules were `pending`, 31 `web-only`).

## 2. Consumption options evaluated against punji-web's setup

| Option | Reproducible | Works in CI and Workers Builds | Matches how releases work | Verdict |
|---|---|---|---|---|
| **Published npm package, exact version** | Yes: version plus lockfile integrity; Trusted Publishing gives provenance | Yes (needs only the registry) | It is the release | **Use for anything that merges** |
| `npm pack` tarball installed with `--no-save` (local loop) | Yes for the bytes (`sha512` of the tarball); not recorded in `package.json` | Not meant for CI | Same artefact that is published (`files`, exports, CSS) | **Use for the local development loop only** |
| Committed tarball (`file:vendor/punji-ui-X.tgz`) | Yes (integrity in lock) | Yes | Not the registry artefact | Fallback only if publishing is delayed; adds a binary of up to 470 KiB unpacked (budget in `scripts/check-pack.mjs`) per bump to git history |
| `file:../punji-ui` (directory) | No: needs a prior build, symlink, path differs per machine | **No**: the sibling repo is absent in CI and Workers Builds | No | Reject |
| `npm link` | No: global symlink, not recorded | No | No | Reject. Also resolves React from punji-ui's tree: two Reacts, "invalid hook call" |
| npm workspaces | Yes inside one repo | Yes | Needs one monorepo; punji-ui and punji-web are separate repos with separate release and CI (`AGENTS.md` rule 1: one repo per task) | Reject |
| Git dependency (`github:20was/punji-ui#<sha>`) | Pinned by sha, but `dist/` is not committed, so install must build: needs devDependencies and lifecycle scripts, which the policy forbids (`npm ci --ignore-scripts`) | Fragile | No provenance | Reject |
| Local registry (Verdaccio) | Yes, if the lock never records it | Not for CI | Exercises real semver and dist-tags | Optional rehearsal of the release flow; never commit a lockfile that resolves to localhost |

### Recommendation

1. **Development loop** (before and between releases): in punji-ui `npm pack` (its `prepack` runs the
   build), then in punji-web `npm install --no-save ../punji-ui/punji-ui-<version>.tgz`. A small
   script in punji-web (`scripts/ui-local.mjs`, new) should wrap this, print the tarball `sha512`, and
   refuse to leave `package.json` or `package-lock.json` modified. It is the exact artefact that would be
   published, so exports, CSS and `use client` behave as in production.
2. **Anything that merges**: depend on a **published** exact version:
   `"@punji/ui": "0.1.0"` (no `^` or `~`), with `save-exact=true` in a new `punji-web/.npmrc`. A bump is
   a one-line PR with the lockfile change. While the package is unpublished, publish a release candidate
   first with Changesets prerelease mode (`npx changeset pre enter rc`, dist-tag `next`) and pin
   `"0.1.0-rc.0"`. This needs the owner to enable the release variable and the npm Trusted Publisher
   (`docs/ARCHITECTURE.md`); I cannot do that.
3. Only if the owner delays publication: commit the tarball as `punji-web/vendor/punji-ui-<version>.tgz`
   and use `"@punji/ui": "file:vendor/punji-ui-<version>.tgz"`; replace it with the registry version at the
   first release.
4. In punji-web CI add `npm audit signatures` (punji-ui already runs it) so a bump verifies the
   provenance attestation.

Peer compatibility: punji-ui peers `react ^19.0.0`, `react-dom ^19.0.0`; punji-web has `~19.2.9` (ok).
Node: punji-ui `>=22.12`, punji-web CI Node 24 (ok). Build tooling for the consumed package: nothing
extra; punji-web's Vite compiles ESM from `node_modules`. Vite warns about the `use client` directives
(`docs/ARCHITECTURE.md`); **unverified** whether punji-web's SSR prerender build does.

## 3. Prerequisites before any module switches (punji-ui side, then punji-web wiring)

### 3.1 Close the API gaps upstream (changeset per item)

From the diffs in COMPONENT-INVENTORY.md; punji-web features missing in punji-ui:

- `Card`: `eyebrow`, `size="lg"` (web CSS `kit-card-eyebrow`, `kit-card-lg`).
- `ListFilter`: `name`, `selectOnFocus`.
- `Rows` `DataRow`: `bar`, `note` slots (`kit-data-bar`, `kit-data-note`, `has-bar`).
- `StatusPill`: tone `info`.
- `CompanySearch`: `clearOnOpen` (ui currently always closes/clears on pick).
- `Button` (and `StatusPill`, `Rows`, `Layout` links): absolute URLs open in a new tab with
  `rel="noopener noreferrer"` and an arrow in web; plain `<a>` in ui. Decide and document one behaviour.
- `compact.ts`: ui hardcodes `Rs`, web uses the reader-language prefix. Make it a parameter.
- `OrderBook`: two different components share a name. Rename one (for example `OrderBookTable` for the
  financial one, or fold the web API into it) before the web module migrates.

punji-ui features missing in punji-web (no work, but they define the target): `Popover` portal mode,
`Select` native-picker enhancement, `DataTable` search/pagination/selection/states, `Field.trailingAction`.
Those need web regression checks, not upstream changes.

### 3.2 Links

All ui link components take `href` and an optional `linkComponent`; punji-web's components use
`react-router-dom` `Link to=`. Add one adapter file, **`src/components/AppLink.tsx`** (new):

```tsx
const AppLink: LinkComponent = ({ href, ...rest }) => <Link to={href} {...rest} />;
```

and, for the four most-used link-bearing modules (`Button` 59 files, `Layout`/`PageHeader`, `Rows`/`ValueRow`,
`StatusPill`), add thin wrappers in **`src/components/app-kit/`** that bind `linkComponent={AppLink}` so the
59-file `Button` change is a codemod of the import path, not of each call site. The same applies to the
8 pending modules that use the router (`CardLink`, `CheckRow`, `LinkRow`, `LinkTable`, `MenuList`,
`MenuPanel`, `ProgressRow`, `SettingRow`).

### 3.3 Tokens and CSS (the largest hidden risk)

- punji-ui reads `--pu-color-*`, `--pu-radius-*`, and so on, defined in `tokens.css` inside
  `@layer punji.tokens`. punji-web's `kit*.css` reads unprefixed variables defined by `me-theme.css` and
  `tokens.generated.css`. Without a map the migrated components render with undefined variables.
- Both define the same `.kit-*` selectors. punji-ui is in `@layer punji.components`; punji-web's
  `kit*.css` is **unlayered**, and unlayered rules beat any layer. While both stylesheets are loaded, a
  migrated component keeps being styled by the old web CSS and a regression (or a fix) is masked.
- Do this once, before the first module switches (the portal bridge already does something similar,
  `scripts/portal.mjs`, layer order `punji.legacy, punji.tokens, punji.components`):
  1. Import `@punji/ui/tokens.css` once in `src/main.tsx`, `src/me/main.tsx` and `src/design/main.tsx`.
  2. Put a token bridge in `src/styles/me-theme.css` (and the public theme) mapping each `--pu-*` to the
     host theme (`--pu-color-bg: var(--color-bg)`, and so on), generated from a checked list, with a
     test that compares resolved values in light and dark. Whether the public host (`--v2-*`, green
     accent `#0F6B4B`) and the account host (lime accent `#C8F23D` dark, `#3F6A00` light in
     `docs/tokens.md`) should look the same is a **design decision I cannot make**; today they are
     different values.
  3. Wrap the web `kit*.css` imports in `@layer punji.legacy` (declared before `punji.components`), so
     punji-ui wins for migrated components; delete a module's rules from the web CSS in the same PR that
     switches the module. `scripts/sync/manifest.mjs` (`CSS_OWNERS`, `SHARED_SELECTORS`) already maps
     classes to the module that owns them; use it to list what to delete.
- Token source of truth must be decided once: `tokens.css` in punji-ui is hand-maintained
  (`docs/tokens.md`: "Maintained with src/styles/tokens.css"), while punji-web vendors tokens from
  `packages/design-tokens/tokens.json` in the app monorepo (ADR-6). Two sources will drift. Options:
  generate punji-ui `tokens.css` from the monorepo file, or make punji-ui canonical and drop `sync-tokens`
  for UI tokens. **Owner decision.**

## 4. Change workflow (one reusable change, end to end)

In **punji-ui**:

1. Branch from `main`; edit `src/`, its CSS in `src/styles/<module>.css`, and tests in `test/`.
2. Port or write tests, including axe checks (every component is axe-tested); add the module's size
   budget in `.size-limit.json` and the export entry in `package.json` and `src/index.ts`
   (`check:exports` fails otherwise).
3. `npm run lint && npm run typecheck && npm test` while working; before pushing `npm run verify:deep`
   (all gates CI runs, plus 2000-input property tests).
4. Visual check: `npm run portal` (existing docs bridge) or `npm run examples`, then the browser checks
   that apply (`CHROME_CHANNEL=chrome npm run check:table` and the others listed in `CONTRIBUTING.md`);
   open every screenshot at 390 and 1440, light and dark.
5. `npm run build`, `npm run check:package` (publint, attw, tarball allowlist).
6. `npx changeset` (patch for fixes, minor for additions; pre-1.0, breaking changes are minor and must
   be called out). Open the PR; CI job "CI OK" is the required check.
7. Merge to `main`. The Release workflow opens "chore(release): version packages"; merging it publishes
   with provenance (requires the owner-enabled variable and the Trusted Publisher).

In **punji-web** (a separate PR, per `AGENTS.md`: one repo per task, worktree from `origin/main`,
conventional commit title `feat(web): ...`, no AI attribution lines there):

8. Before the release exists, use the local loop (section 2, item 1) to try the change; do not push it.
9. After release: change the pin (`npm install --save-exact @punji/ui@<version>`), commit
   `package.json` and the lockfile only, and the code that adopts the change.
10. Run the local gates of `AGENTS.md` section 3: `npm run typecheck`, `npm run lint`, `npx vitest run`,
    `npm run check-contracts`, `npm run check-tokens`, plus the new `npm run check:ui-single-source`
    (section 5). Screenshot every touched page and state at 1440, 1024 and 390 in light and dark.
11. Merge; production deploys on merge to `main` (Workers Builds), not by hand.
12. Rollback: revert the pin commit; because the version is exact, no other state changes.

Rule of thumb: **the first punji-web PR for a component is the one that deletes the web copy.** A
change is never made in both places.

## 5. Preventing two sources of truth

All new files below are in punji-web and are proposals; nothing was written there.

1. **Migration ledger** `scripts/kit-migrated.json` (new): every module that now comes from
   `@punji/ui`, with the version it moved at.
2. **Check** `scripts/check-ui-single-source.mjs` (new, wired as `npm run check:ui-single-source` and
   added to `web-ci.yml` next to `check-contracts`): fails if any ledger module still exists under
   `src/components/kit/`, if any file imports a ledger module by relative path or by a local alias, if
   `package.json` has a range (`^`, `~`, `*`, `latest`) for `@punji/ui`, or if `tsconfig.app.json`
   `paths` still maps a ledger module.
3. **Lint** in `eslint.config.js`: `no-restricted-imports` patterns for `**/components/kit/<Migrated>`
   (generated from the ledger).
4. **Shrinking alias**: `scripts/punji-ui-alias.mjs` stops globbing the directory and lists only residual
   local modules; `tsconfig.app.json` `paths` shrinks the same way; `punji-ui-alias.test.mjs` and
   `kitOnly.test.ts` are updated. At the end the alias file is deleted.
5. **Rename the remainder**: the 31 app-specific kit modules (`AppTabBar`, `SiteHeader`, `Logo`, broker
   and alert components, and so on) move to `src/components/app-kit/` so `kit` no longer suggests a
   shared library. `AGENTS.md` rule 6 and `docs/web/UI.md` are reworded: "the design system is the npm
   package `@punji/ui`; app components compose it".
6. **Retire what is left of the sync in punji-ui** once the last module is migrated: delete
   `scripts/sync-from-web.mjs` (already throws), `scripts/sync/manifest.mjs`, the `sync` script, the
   `sync-*.md` changesets history stays; keep `audit:web` only until cut-over (it is the divergence
   report) and then remove it with `docs/audit/inventory.json` and `component-matrix.md`.
7. **CODEOWNERS or PR template** in punji-web: a PR touching `src/components/app-kit/**` that adds a
   visual component not specific to Punji must link a punji-ui issue (the existing rule 6: "if a page
   needs something the system lacks, add it to the system first").
8. **Version-skew guard** in punji-ui: nothing new is needed because releases are immutable on npm and
   punji-web pins exactly.

## 8. Moving the docs portal out of punji-web

Today the portal is `src/design` in punji-web, and punji-ui's `portal/` and `scripts/portal.mjs` patch
it in memory (routes, registry, three CSS and import rewrites; the bridge throws if the shell changes).
That is a stop-gap; the target is a standalone portal in punji-ui.

1. **Create the app in punji-ui** (`portal/`, already holds `pages.tsx`, `calendar-pages.tsx`,
   `select-page.tsx`, `registry.mjs`): copy the shell from `punji-web/src/design` (`App.tsx`, `main.tsx`,
   `registry.ts`, `gallery.tsx`, `parts.tsx`, `design.css`, `site.ts`, `searchIndex.ts`, changelog
   parts). Import the package through its public specifiers (`@punji/ui/...`, as `scripts/check-exports.mjs`
   already does), never through source paths.
2. **Move pages with their components**: each migration PR in section 6 moves that component's docs
   page (`src/design/pages/*.tsx`) and removes its registry entry in punji-web. Pages for the 31
   app-specific modules and the product `docs.tsx`/`brand.tsx` pages stay in punji-web or become
   markdown under `docs/web/`; **owner decision** (the portal in punji-ui must not document code it does
   not ship).
3. **Generate API tables from punji-ui source**: port `scripts/design-props.mjs` to read `src/**`, and
   take sizes from `.size-limit.json`/`size-limit --json` instead of `kit-size.mjs`. Remove
   `props.generated.json`, `prop-names.generated.json`, `sizes.generated.json` from punji-web with the
   scripts.
4. **Build and host separately**: a static build of the portal (for example `npm run build:portal`,
   output ignored by git) deployed from punji-ui's own CI to `design.punji.app` (Cloudflare static assets
   or Pages; the repository has no deploy workflow today, and `docs/ARCHITECTURE.md` lists the docs hosting
   decision as open). Until then keep `design.punji.app` served by the web Worker; then remove
   `DESIGN_HOST`, `worker/pages/design.ts`, `design.html` and the `--mode design` build from punji-web in
   one PR, after DNS points to the new host.
5. **Retire the bridge**: delete `scripts/portal.mjs`, `portal/bridge.d.ts` and the in-memory patches once
   step 1 is live; update `portal/README.md`, `docs/audit/PORTAL-VALIDATION.md` and the `portal`,
   `typecheck:portal`, `check:portal` scripts.
6. **Docs-site tests**: `src/design/__tests__` (punji-web) move with their pages; the browser checks
   (`check:portal`, `check:select`, `check:table`, and so on) already live in punji-ui.

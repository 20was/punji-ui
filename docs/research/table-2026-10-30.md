# Search and pagination research

Date: 2026-10-30. The aim was to add a usable search and pagination interface to Punji's existing table API without adding a runtime dependency or binding the component to one application's row model.

## Reviewed sources

- [TanStack Table global filtering guide](https://tanstack.com/table/latest/docs/framework/react/guide/global-filtering): its table core supplies filtering state and row-model features but leaves the search input UI to the application. It distinguishes client filtering over the full data set from manual server filtering.
- [TanStack Table pagination guide](https://tanstack.com/table/latest/docs/framework/react/guide/pagination): client pagination slices a complete row model; manual pagination consumes already paginated server data. The pagination state uses a zero-based page index.
- [TanStack filtered row model source](https://github.com/TanStack/table/blob/main/packages/table-core/src/features/column-filtering/createFilteredRowModel.ts) and [pagination feature utilities](https://github.com/TanStack/table/blob/main/packages/table-core/src/features/row-pagination/rowPaginationFeature.utils.ts): filtering is a row-model stage and filtering changes reset pagination; page-index updates are clamped and no-op resets avoid unnecessary change callbacks.
- [TanStack row-selection guide](https://tanstack.com/table/latest/docs/guide/row-selection) and [row-selection API](https://tanstack.com/table/latest/docs/api/features/row-selection): selection state is caller-controlled, stable row IDs are recommended, the header can target only the current page, and the library leaves rendering of selection controls to the application. The guide calls out that server/manual pagination can only derive loaded rows, so off-page selected IDs stay in the controlled selection map rather than an inferred current-page row model.
- [Filtering implementation tests](https://github.com/TanStack/table/tree/main/packages/table-core/tests/implementation/features/column-filtering) and [pagination implementation tests](https://github.com/TanStack/table/tree/main/packages/table-core/tests/implementation/features/row-pagination): the project tests row-model behavior separately from framework examples.
- [TanStack Table package metadata](https://github.com/TanStack/table/blob/main/packages/table-core/package.json), [MIT licence](https://github.com/TanStack/table/blob/main/LICENSE), and [release history](https://github.com/TanStack/table/releases): current core metadata declares MIT, has explicit ESM exports and `sideEffects: false`; the release stream is active. No TanStack code or dependency was added to Punji UI.

## Decision

Punji UI's `DataTable` remains a semantic, styled table. Search, pagination and selection are optional controlled UI contracts; the consumer owns filtering, sorting, selection state, and data operations. `FinancialTable` forwards those props and maps its stable `rowKey` into selectable row IDs. Select-page touches only visible rows, while off-page or filtered IDs remain controlled by the caller. This follows TanStack's controlled state and page-scoped header selection patterns without taking a dependency.

The search action resets a later page to index zero. Empty results retain the search field, table headers and result count. Loading keeps the caption and headers, exposes `aria-busy`, and provides a live status. The page controls use a named navigation landmark and the search/clear controls have accessible names. All values remain React-rendered text/nodes; queries and records are never logged.
